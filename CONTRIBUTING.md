# Contributing

Thanks for helping maintain Command Variable. This document covers the local
workflow, the test strategy, and the checks that run in CI.

## Quick start

The toolchain is pinned in `.tool-versions` (asdf format), so if you use asdf
the right Node version is selected automatically:

```bash
asdf plugin add nodejs   # one-off, if you have never installed the nodejs plugin
asdf install
```

Any Node 22 install works if you'd rather not use asdf.

```bash
npm ci          # installs dependencies and generates the local vscode test shim
npm run verify  # lint + unit tests + coverage + build + bundle check + audit
```

## Repository layout

| Path | Purpose |
| --- | --- |
| `extension.js` | Desktop extension entry point (uses Node APIs). |
| `extension-common.js` | Shared logic; compiled by rollup into the web entry point. |
| `utils.js` | Pure helpers, no extension-host state. |
| `uuid.js` | Vendored UUID library. |
| `yaml.js` | Vendored `yaml` bundle (see [Vendored dependencies](#vendored-dependencies)). |
| `uuid-org.js` | Upstream copy of the UUID library. **Not used by the build.** |
| `out/extension-common.js` | Generated by rollup; declared as the `browser` entry point. |
| `test/unit` | Fast tests, run in-process with a stubbed VS Code API. |
| `test/integration` | Tests run inside a real VS Code Extension Host. |
| `scripts/` | Maintenance tooling (bundle check, packaging, shim generation). |

Anything in the top-level directory other than `extension.js`, `utils.js`,
`yaml.js`, `uuid.js` and `out/` is build or maintenance tooling and is excluded
from the published `.vsix` by `.vscodeignore`.

## Testing

There are three layers. Prefer the cheapest layer that can express the assertion.

### Unit tests (the default)

```bash
npm run test:unit        # no coverage, fastest
npm run test:coverage    # with coverage thresholds enforced
npx vitest --watch       # watch mode while developing
```

These run in plain Node in a few hundred milliseconds. They work because
`utils.js`, `extension-common.js` and `extension.js` call `require('vscode')` at
module scope, and `scripts/install-vscode-stub.js` places a test double at
`node_modules/vscode` so that import resolves outside the Extension Host.

- The test double lives in `test/helpers/vscode-stub.js`.
- The generated shim is wired into `postinstall`, so `npm ci` sets it up. The
  test scripts also regenerate it defensively, because `npm prune`/`npm audit
  fix` can delete it.
- The stub records every call, so tests can assert on what the extension asked
  VS Code to do, for example `vscode.__calls('window.showErrorMessage')`. The
  stub's test-only helpers (`__calls`, `__setResponse`, `__invoke`,
  `__reset`) are defined at the bottom of `test/helpers/vscode-stub.js`.

Coverage thresholds in `vitest.config.mjs` are set just below the current level.
Raise them when you add tests rather than leaving headroom. Re-measure after
upgrading Vitest: the v8 provider counts branches differently across majors.

### Integration tests (real Extension Host)

```bash
npm run test:integration
```

This downloads VS Code, builds the extension, opens the fixture workspace in
`test/fixtures/workspace`, and activates the extension for real. It verifies the
things a stubbed host cannot: activation succeeds, every declared command
actually exists at runtime, and commands execute end to end.

These are slower and need a display on Linux; `xvfb-run -a npm run
test:integration` handles that, and the wrapper script does it automatically when
`CI` is set.

### Dev container

`.devcontainer/` provides an isolated environment with the OS libraries Electron
needs. This keeps VS Code downloads and Extension Host processes off your host
machine:

```bash
# In VS Code: "Dev Containers: Reopen in Container"
# Or with the devcontainer CLI:
devcontainer up --workspace-folder .
devcontainer exec --workspace-folder . npm run verify
```

Docker must be running. If you do not have Docker, the repository works fine
directly on macOS, Linux or Windows.

## Maintenance tests

`test/unit/manifest.test.js` contains guardrails that catch the usual ways a
lightly-maintained extension rots. They are cheap and fail with an explanation:

- **Manifest contract** — every `onCommand` activation event is registered, and
  every registered command has an activation event. Catches commands that are
  dead in the manifest or broken at runtime.
- **Dynamic eval budget** — the `${...}` expression features intentionally use
  the `Function` constructor. The test pins the exact number of eval sites so a
  new one is a deliberate, reviewable decision.
- **No shelling out, no network** — asserts the extension never imports
  `child_process` or `http(s)` and never calls `fetch`.
- **Bundle discipline** — `scripts/check-bundle.js` asserts `out/extension-common.js`
  requires only `vscode` (any Node built-in would break the web extension host)
  and stays inside a size budget.
- **Type/engine alignment** — `@types/vscode` must not be newer than
  `engines.vscode`, which is the rule `vsce` enforces at packaging time.

## Vendored dependencies

`yaml.js` is a rolled-up copy of the `yaml` package rather than a declared
dependency, so Dependabot cannot see it. The version it was built from is
recorded in the `vendored` field of `package.json` and asserted by a test.

To update it, replace `yaml.js`, update the `// module: "yaml": "x.y.z"` comment
at the top of the file, and update the `vendored.yaml` field in `package.json`.
All three are checked together.

`uuid-org.js` is a full upstream copy of the UUID library that the build does not
consume. It is excluded from lint and from the `.vsix`; it is a candidate for
deletion.

## Releasing

```bash
npm run verify     # everything must be green
npm run package    # writes dist/<name>-<version>.vsix and prints its size
code --install-extension dist/command-variable-*.vsix   # smoke test locally
```

Then bump `version` in `package.json`, add a matching `## [x.y.z] yyyy-mm-dd`
entry to `CHANGELOG.md` (a test asserts the version appears in the changelog),
and tag the release.

To publish:

```bash
npx vsce publish
```

Publishing is intentionally not automated: it needs a Marketplace personal
access token, and a human should confirm the changelog and smoke test first.

## Keeping this maintained

- Dependabot opens grouped monthly PRs for npm and GitHub Actions.
- `npm test` is an alias for `npm run verify`, so a single command is enough
  before any commit.
- When VS Code raises its minimum engine, bump `engines.vscode` and the
  `@types/vscode` range together, then re-run `npm run verify`.
